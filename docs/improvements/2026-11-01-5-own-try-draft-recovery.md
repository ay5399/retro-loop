# 未保存の本人Try入力を再読み込み後に復元する

## 観測と選択

添付ベースラインには本人の行動・日付を入力して確認保存する欄がある。既存の `own-try-confirmation.tsx` は両項目をuseStateだけで保持しているため、再読み込みでは失われる構造だった。実行による変更前再現、発生頻度、被害件数、利用者インタビューは未確認。入力喪失が確認保存までの手戻りになるという影響は仮説である。

候補①は未保存の本人Try下書き復元。本人のProblemから本人が決めた行動を確認保存する優先シナリオに直結し、DB変更なしの小さな変更で実装できる。候補②は元Problemとの構造化関連と完了管理。広い効果を期待できるが、保護対象DBを含む専用作業が必要になる。承認済み計画どおり①だけを実装した。競合への機能追随を目的にはしていない。

## 調査（2026-11-01閲覧）

- https://www.goretro.ai/help-articles/create-follow-up-on-action-items : カードからアクションを作り、担当者・期限・説明を指定できる。製品公式説明であり、下書き喪失のユーザー証拠ではない。
- https://easyretro.io/whats-new/ : 2026-08-31の更新に、同じチームの他ボードの未完了アクションを本文・担当・期限・元ボード付きで再表示する機能がある。保存されたアクションの継続性を示すが、RetroLoopの一時入力復元の効果を実証しない。
- https://docs.pagerduty.com/ops-guides/retrospectives/after : 未進捗のアクションについて責任追及せず原因を確認する実務ガイド。直接取得は失敗し、検索結果の抜粋で該当記述を再確認した。
- https://retrospectives.pagerduty.com/facilitator_training/ : 実務ガイドの検索結果で、アクションの担当を決め、次回に進捗を確認する助言を確認。実践知でありRetroLoop参加者の観測結果ではない。
- https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage : オリジンとタブごとの一時保持で、再読み込みをまたぐ。タブ終了後の復元やサーバー保存を保証する仕組みではない。アクセス制限や容量不足に備える。
- https://nextjs.org/docs/app/getting-started/server-and-client-components : インストール済みnext/dist/docsの同ガイドを先に読み、認証済みServer Componentから文字列の本人IDをClient Componentへ渡し、ブラウザーAPIはマウント後に使用した。
- https://ai-sdk.dev/docs/ai-sdk-ui/chatbot : インストール済みai/docsのChatbotガイドと@ai-sdk/react/src/use-chat.tsの型を先に確認。AI送信・状態管理は変更せず、本人が入力した行動・日付だけを保持する。

## 変更後の動作と境界

本人IDは認証済みページからAiChatへ渡す。本人・チーム・ふりかえりのID配列をJSON化したバージョン付きキーでsessionStorageを分離する。これは保存先の分離であり認可の代替ではない。既存のServer Actionの認証・チーム認可とプロバイダー境界は変更しない。合成画面には架空の本人IDだけを追加した。

初期復元中は編集を無効にし、空値を書き込むeffectは設けない。本人の入力イベントでだけ行動・日付を同期的に保持する。復元は常に編集段階で、確認段階・AI応答・チャット履歴を復元しない。本人が確認して明示保存するまでDB書込もAI送信もしない。成功時または明示破棄時に下書きを削除し、保存失敗時には保持する。不正データ・保存領域の例外でも通常入力を続けられる。一時保持とTry付箋の保存を画面で区別する。

## 回帰検証と証拠

既存E2E本文・アサーションには触れず、`e2e/own-try-draft-recovery.spec.ts` を追加した。

- 改行付き行動・日付の完全一致復元、確認段階からの再読込で編集へ戻ること、復元だけではAI要求・Try作成がないこと。
- 修正・確認・明示保存後に、本人作成のTryが一件だけDBとボードに残り、下書きが復活しないこと。
- 保存失敗後の復元、明示破棄、別本人・別ふりかえり・別チームキーの分離。
- 不正JSON・型・日付形式、初期復元の上書き防止、部分入力、アクセス例外・容量不足からの通常確認保存。

新規テストが作成する画像は `e2e/__screens__/own-try-draft-recovery-before.png`（入力後・再読み込み前）と `e2e/__screens__/own-try-draft-recovery-after.png`（復元・修正・保存・再表示後）。beforeは同じ改修版の操作前段階であり旧SHAの画像ではない。画像は未生成。

ホストでアプリ、SDK、ビルド、テストを実行していない。静的差分確認だけを実施。型検査・lint・ビルド・既存と新規のモックE2Eはcontrollerの使い捨てGitHub-hosted runnerで実行予定であり、成功を主張しない。

## 独立レビューと実AI検証

企画は本依頼に記載された独立承認済み計画に従った。実装に対する独立Claudeレビューは未実施、指摘と対応は未受領。controllerがレビュー結果と修正対応をこの記録に追記する。

AI画面変更として、独立レビュー後の同一SHAで既存Plus認証・架空データ・最大3往復のPC内一時画面検証をcontrollerが実施する。今回この工程は実行していない。本人入力の再読み込み復元から確認保存までを確認し、モデル・認証経路・応答・遅延・未完了範囲を記録する。ブラウザー内合成保存と、本番認証・DBを使うモックCIの検証を区別する。接続成功だけで体験合格としない。

## 残る制約と週次判断

タブ終了後の復元、チャット履歴保持、保存応答喪失時の重複防止、構造化Action管理は対象外。同一オリジンのスクリプトから読めるブラウザー内一時データであり、秘密の保管庫ではない。ブラウザーが削除も拒否する場合は下書き消去を保証できない。週次では一時保持の有用性・保持範囲と、次に構造化Action管理へ進めるかを判断する。
