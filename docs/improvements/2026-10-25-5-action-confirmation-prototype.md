# 本人が確定するアクション確認カード（隔離実験）

## 観測と選択

添付 ai-chat / board-color / board-group / board-vote の4画面はKPT操作と汎用チャットが中心。既存 ai-chat.tsx は本人のProblemを編集可能な相談文に追加できるが、相談後に行動・担当・日付を確認し保存・再表示する導線はない。利用者が実際に転記に失敗したという観測ではなく、画面とコードの観測である。

| 候補 | 優先シナリオへの一致 | 実現性 | 期待影響（仮説） |
| --- | --- | --- | --- |
| A 待機・失敗表示の改善 | 相談継続を支えるが保存の途切れは残る | 高い | 離脱を減らす可能性 |
| B 本人入力の確認・保存カード | 本人の一件を確認・保存・再表示できる | DB変更なしの隔離画面なら高い | 誰が・いつ・何をするか確認できる可能性 |

Bのみ採用。競合との機能同等化は目的にしない。

## 挑戦する前提・比較

「AIの助言を読めば本人が実行可能なTryへ転記できる」を問い直す。仮説：本人が行動・日付・本人担当を明示確認するカードがあれば、自由文のみより、一件の保存と再確認まで進める。実利用での改善は未検証。

`/experiments/action-confirmation` は環境変数を読まない静的な入口。認証・DB・製品チャット・API・LLMをインポートしない。通常画面からリンクせず、固定モック3問・架空Problem・架空ユーザーだけを表示する。URLを知れば表示できる実験画面であり、アクセス制御は提供しない。この作業では公開しない。比較スイッチは同じProblemと同じ3返答を使い、自由文のみと確認カードありを比較する。既存画面の忠実な再現や対照実験の結果ではない。

行動・日付は空欄から本人が入力する。返答から抽出・補完しない。修正すると本人確認を解除する。未確定なら保存を止める。一つのProblemに一件を明示保存し、元Problem・行動・本人・日付・未着手を再表示、完了への変更も保存する。実験ユーザーとふりかえり別のlocalStorageキーを使い、切替時はセッションを再作成する。これは認可境界ではなく架空データの表示分離。同一オリジンのスクリプトは保存内容を読める。読込失敗時は上書きを止め、書込失敗時は成功表示しない。対話履歴と未保存の入力は再読み込みで消える。

## コントローラーでの検証手順（訂正2の差分は未実行）

既存Playwright設定のモックAI・ダミーPostgreSQL・使い捨てrunnerで `e2e/action-confirmation.spec.ts` を実行する。ホストでアプリ・ビルド・テストを実行していない。

1. 同じ架空Problemと返答で自由文比較画面を撮影する。
2. 3往復後も行動・日付が空欄、日付なしでは保存不可であることを確認。
3. 本人入力を修正すると確認が解除され、再確認後のみ保存する。
4. 二重操作でも一件だけ保存し、再読み込みで元Problem・行動・本人・日付・未着手が一致することを確認。完了も再読み込みで確認。
5. 別の実験ユーザー／ふりかえりで非表示、元の組合せへ戻ると再表示する。
6. 初回保存例外では成功表示せず再試行できること、完了の保存例外では未着手の表示と保存内容を維持することを確認する。
7. 壊れたJSON・存在しない日付・別ふりかえりの保存レコード・ブラウザー保存の読込拒否では、保存済み表示や上書きをしないことを確認する。
8. 全シナリオでAPI／外部HTTP要求を遮断し、試行された場合も失敗とする。対話が3往復で止まることを確認する。これはブラウザーHTTP要求の検査であり、既存Next開発サーバー全体の通信を監査するものではない。

### 訂正1：コントローラー指摘と対応

- 提供された指摘は `New external calls or runtime credential access require owner approval`。独立レビューの内容は `undefined` で、具体的なClaude指摘は提供されていない。どの箇所が検出原因かはログから断定できない。
- 実験ページにあった `process.env.AUTOMATION_TEST` の実行時参照を削除。これは認証情報ではないが、実験コードに環境変数の読取自体を不要とする。新しい外部呼出し・認証情報参照・依存関係は追加しない。固定モックは単なる文字列配列で、ネットワーク処理を持たない。
- 全Playwrightシナリオに同一オリジン限定／API要求拒否を適用。保存レコードにふりかえり識別子を含めて照合し、実在する暦日だけを許可。読込破損・拒否と完了更新の書込失敗のシナリオを追加した。
- 調査4資料を2026-10-25に読み直し、GoRetroの取得できない詳細について記述を限定した。資料閲覧は公開Webの読取調査であり、アプリの外部連携ではない。
- 静的確認：変更は実験画面2ファイル、Playwright1ファイル、本記録1ファイルのみ。`git diff --check` と `git diff --cached --check` は問題を出力しなかった。ホスト上でアプリ、ビルド、テストを実行していない。保護対象を変更していない。追加許可が必要な実行時処理を除去したため、承認を求める操作は残していない。

### 訂正2：独立レビューと検証失敗への対応

- ユーザー提供の独立ClaudeレビューはSHA `6425fe713b2a8791f72600cb0bdc33ed20720f76` に対し `approve` / `reversible`。固定モック、本人入力、確認解除、二重保存防止、失敗時の停止を評価した。今回の修正後SHAを承認したものではない。
- 指摘1（レイアウト・middlewareの認証/API要求の可能性）：ルートレイアウトはフォント・CSSとchildrenのみ。今回のツリーにはmiddleware/proxyファイルがなく、実験入口も認証/APIをインポートしない。API拒否と外部要求検査は弱めず維持した。到達性はrunnerで再確認する。
- 指摘2（Storage.prototypeの全面差し替え）：読込拒否はlocalStorageかつ実験キーのときだけ発生するよう限定した。sessionStorageと無関係のlocalStorageキーは元の実装へ委譲する。拒否後の書込試行数が0であること、および無関係の保存・読出しが使えることをPlaywrightで検証する。保存失敗の注入もlocalStorageの実験キーに限定する。
- 初期HTMLでは実験条件のfieldsetを無効化し、ハイドレーション後に有効化する。比較チェックの操作がReactのハンドラー接続前に行われる不安定要因を除いた。テストは実験条件の有効化と、比較切替後の確認カードの有無を明示的に待つ。
- 指摘3（URLで開ける実験）：架空データ専用、通常導線から未リンク、ブラウザー内保存という境界を維持。本番認可を実装したとは扱わない。公開・マージ・デプロイは行っていない。
- 提供されたコントローラーログ（run `40129033442`）では依存導入、DB migration、check、automation tests、buildは成功し、`test:e2e` が失敗。その後の画像収集・artifact uploadはスキップされた。ログはジョブ進捗のみで、テスト名・スタックトレースは含まれない。したがって失敗原因を断定せず、今回の変更でE2Eが成功したとも主張しない。Node 20/Ubuntuの注意は保護対象の自動化設定に関するため変更していない。
- ホストでは読取・編集と `git diff --check` のみ実施し、アプリ・ビルド・テスト・実AIは実行していない。証拠PNGはrunnerの再実行で生成する予定であり、この訂正の成功証拠はまだない。4資料を2026-10-25に再確認した。
