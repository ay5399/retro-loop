# 実AI検証の失敗と再開

実AI検証の失敗だけを根拠にアプリの修正生成を始めない。候補SHA・独立レビュー・計画を `live-ai-blocked` として保持し、結果は `awaiting-verification`（終了コード2）にする。アプリの確定したCI失敗は従来の修正経路を維持する。

- 利用上限: 推論前に `account/rateLimits/read` を読み、100%の枠があれば推論しない。取得できたリセット日時以降に同じ候補の検証を再開する。日時不明なら調査待ち。
- 通信・サービス障害: app-serverの構造化エラーを分類し、次回起動で候補の検証だけを再開する。
- 文言検査、画面検査、検証器の障害、情報欠落: 原因未確定として保持する。検査失敗をアプリの不具合とは断定しない。
- 自動での再検証は候補の引き継ぎ全体で最大2回。以後は調査待ち。診断後の手動 `--retry-live-verification --recover-only --manual-run` は1起動につき1回だけ再検証し、コード生成・承認境界解除をしない。

再開時は元worktreeのSHAとclean状態を検査する。main追従でSHAが変わる場合は独立レビューをやり直す。実AI、CI、PNG、既存の公開条件をすべて満たすまで公開しない。復旧を完了した実行では新しい改善を始めない。`--recover-only` は未完了候補の復旧だけを行う。

旧ランナーの `needs-fix` / `review` に同一SHAの失敗した実AI記録が残る場合は、新しい実行のcheckpointだけを変換する。元の失敗記録は変更しない。承認待ち・レビュー拒否にはこの変換で介入しない。

上流エラーは種別・HTTPステータス・リセット日時だけを追加保存する。アカウント情報や認証情報を含み得るエラーメッセージ全体は保存しない。画面側でエラーストリームへ変換されても推論失敗の記録を残す。

これは任意の障害を無人で解消する仕組みではない。保護対象の検証器の修正や原因不明の検査失敗には診断が必要であり、その間に別機能の生成や費用の増える経路への切り替えは行わない。公開・CIの結果が不確定な場合も、元候補を保持して調査する。
